Scope: packaging, signing, update delivery, clean-install verification and real-project regression. No new editing
features and no film-format changes.

## Blockers

- [ ] macOS Developer ID signing and notarization completed with real certificates
- [ ] Windows code signing completed with a real certificate
- [ ] Update feed deployed and verified at `https://set.tryworld.com.cn/updates`
- [ ] Release workflow produces a signed candidate without an unsigned fallback

The signing and feed code is implemented. Until the checklist items above are checked, the public `v0.3.0` artifacts

download page. They are deliberately marked as an Alpha draft until the operating entity, registered address,
contact route, governing-law details and paid-license terms are confirmed. Do not describe them as final terms or
as legal advice.

## Signing inputs

These are the GitHub Actions secret names. Do not claim a signed release until
`pnpm release:preflight --require-signing` passes in an environment with all of them set, and the workflow has produced
a candidate whose signatures were checked.

| Secret | Purpose |
| --- | --- |
| `SETPIECE_SIGN_IDENTITY` | Developer ID Application identity, such as `Developer ID Application: Name (TEAMID)` |
| `APPLE_TEAM_ID` | Apple Developer team ID |
| `APPLE_CERTIFICATE_P12` | base64-encoded Developer ID Application `.p12` |
| `APPLE_CERTIFICATE_PASSWORD` | password for the `.p12` |
| `APPLE_NOTARY_APPLE_ID` | Apple ID used for notarization |
| `APPLE_NOTARY_PASSWORD` | app-specific password for that Apple ID |
| `WIN_CSC_LINK` | base64 or URL for the Windows code-signing certificate |
| `WIN_CSC_KEY_PASSWORD` | password for the Windows certificate |
| `CLOUDFLARE_API_TOKEN` | deploy token for the `tryworld-set-download` Worker |

## Update feed

The desktop app looks for updates under `product.official.json`:

```text
https://set.tryworld.com.cn/updates/mac/arm64/latest-mac.yml
https://set.tryworld.com.cn/updates/mac/x64/latest-mac.yml
https://set.tryworld.com.cn/updates/win/x64/latest.yml
```

The beta channel uses `beta-mac.yml` and `beta.yml` in the same folders. The archives stay on GitHub Releases; the feed
files are generated by `scripts/prepare-update-feed.mjs` and deployed by `.github/workflows/update-feed.yml` only after
the GitHub release is published. Never publish a feed whose checksum or size does not match the uploaded archive.

Current state: the URL is configured and the deployment workflow is present. The route is not live until the first
published release runs the feed workflow with `CLOUDFLARE_API_TOKEN`; verify the three YAML files with `curl` before
calling the updater complete.

## Go/no-go

Ship only when:

- every blocker above is checked;
- CI is green on the exact commit being released;
- the uploaded installer hashes match the tested bytes;
- macOS `codesign --verify --deep --strict` and `spctl` pass;
- Windows shows a trusted publisher or the residual warning is explicitly accepted;
- the updater can move from the previous release to the candidate and back to the previous build without losing data.

## Release workflow sequence

1. Set the signing secrets and `CLOUDFLARE_API_TOKEN` in GitHub Actions.
2. Push a version tag or run `release.yml` against an existing tag.
3. Review the draft release and its `SHA256SUMS.txt`.
4. Publish the release. `update-feed.yml` chooses `beta` for a prerelease and `stable` otherwise.
5. Confirm the three feed files and their SHA-512 values before announcing the build.
